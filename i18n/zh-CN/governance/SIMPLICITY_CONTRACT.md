# 简洁契约（SAE V3.4）

> [English](../../../governance/SIMPLICITY_CONTRACT.md) 为规范版本 | 简体中文译本

**地位：** 对所有角色有约束力。其他 SAE 文档、模板或 Issue 要求的代码、测试、检查或证据超出本契约时，**以本契约为准**，除非 Issue 写明了需要额外工作的具体风险（§5）。

## 为什么需要
V3.3 下，Engineer Agent 写出的代码远超科研需要：手写 JSON 校验器、对 provider 输出逐字符检查可打印 ASCII、用 `ast` 解析驱动脚本、自定义错误码体系、测试文件比被测代码还长，以及为一条 25 行的验收标准提交约 1.7 万行证据。这些都没有让结果更可信，却消耗了 Engineer 的时间、审查者的注意力和可维护性。

根源在框架本身：每份文档都在重复防御性要求，没有任何地方说"够了"，而审查只会要求"更多"。V3.4 反转默认：**能满足完成标准的最小改动，就是正确的改动。**

## 1. 代码：内部信任，边界校验
1. **先写最直接的版本。** 普通函数、标准库和 PyTorch 惯用写法。在出现第二个真实调用方之前，不引入抽象、类、注册表、插件点或配置项。
2. **只在信任边界校验**——数据来自用户（CLI 参数、配置文件）、网络或外部工具输出的地方——而且只校验程序真正用到的字段。其余一律信任。
3. **内部代码信任内部代码。** 不对自己代码产生的值重复做 `isinstance` / 形状 / dtype 检查；调用方已校验的参数不再校验。让 Python 和 PyTorch 自己报错。
4. **只有在会因此做出不同处理时才捕获异常**（重试、回退、清理、面向用户的提示）。禁止捕获后换个名字再抛出。除非有真实消费者按错误码分支，否则不建自定义错误码体系。
5. **不做臆测性健壮化：** 不处理所述用途中不可能出现的输入，不加"保险起见"的长度上限，不写重复键 JSON 解析器，不做字符集过滤，不做防御性拷贝，不给本地纯 Python 代码加超时。
6. **先删再加。** 改动让某段代码过时时，在同一个 PR 里删掉它。

### 禁用模式（除非 Issue 写明风险）
| 模式 | 改为 |
| --- | --- |
| 对自己脚本输出的 JSON 手写 schema 校验 | `json.loads` 后直接用字段；`KeyError` 就是合格的失败 |
| 用 `ast` / 正则解析自己的源码来强制约定 | 普通常量或函数参数 |
| 每个内部函数都重复检查形状/dtype | 在张量进入公共 API 处检查一次，或不检查 |
| `try/except Exception` → 自定义错误字符串 | 直接抛出；traceback 就是证据 |
| 给每个 subprocess 调用包一层自制重试/解析 | `subprocess.run(..., check=True)`；只在实际观察到 provider 不稳定时重试 |
| "以后可能用到"的新模块、类或 CLI 参数 | 不写 |
| 没人要求的备份文件、dry-run 模式、快照、回退路径 | 不写 |

## 2. 测试：只测真正可能出错的地方
1. **每个改动的行为写一个测试**，该行为坏掉时它会失败。这是默认值；更多需要理由。
2. **数值代码：** 用一个*独立*参考（如稠密 `torch.linalg`、闭式解、文献数值）做 oracle 测试，取一个小规模和一个实际规模，用关键的 dtype。只有当数学上存在已知的奇异/退化区间时才加边界用例。
3. **不要测：** 参数校验、第三方库、PyTorch 本身、日志/格式化、文档、简单 getter，以及外部 CLI 的 mock（解析一份真实捕获输出除外）。
4. **不写随机/对抗/性质测试套件**，除非 Issue 要求或算法存在已知稳定性风险。
5. **预算：** 新增测试行数 ≲ 新增源码行数。测试文件比被测代码还长，是审查警示。
6. **只跑涉及改动的测试。** 只有共享代码或依赖改变时才跑全量。

## 3. 证据：Git 就是完整性层
1. 精确 commit SHA 已标识每个被跟踪的字节。**禁止**对 Git 跟踪文件做哈希清单，禁止写"被测版本 vs 最终版本"一致性报告。只对 Git 之外的字节（下载产物、wheel、外部数据集）记录一行 SHA-256 + 大小。
2. 在**最终 HEAD** 上测试。证据写在 PR 交接评论里。
3. 仓库证据上限：

| 改动 | 证据 | 提交到仓库的文件 |
| --- | --- | --- |
| 文档 / 配置 | diff 本身 | 无 |
| 代码 | 测试命令、通过/失败数、一行环境、最终 SHA | ≤ 3 个文件，≤ 200 KB |
| GPU / 计算实验 | 上述 + 实际观测到的设备、被结论引用的结果数据、会话清理回读 | ≤ 10 个文件；只有被结论引用的原始数据 |

4. **失败写成列表**，不建目录：在 PR 评论里写 `尝试 — 原因 — 修复`。只有失败本身是科研结论时才提交失败日志。
5. **复用环境检查。** 机器、工具链和 pin 未变 → 一行"环境自 <SHA> 起未变"。真正分配前仍实时检查 Colab 认证和会话状态。

## 4. 派活：由 Architect 定预算
每个 Engineer Issue 写明四件事（见 [Issue 模板](../templates/ISSUE_TEMPLATE.md)）：
1. **完成标准** — 可观察的，一到三条。
2. **规模预算** — `S`（净增 ≤ 50 行）、`M`（≤ 200）或 `L`（≤ 500），源码 + 测试合计。
3. **必需测试** — 精确清单，通常一到三个。
4. **不需要做** — Engineer *不应*花精力的事项。

若将超出预算 1.5 倍以上，Engineer **停止追加**，交付满足完成标准的部分，把省略的额外内容作为建议列在 PR 里。指令含糊时，取**较轻的理解**并用一行说明。

## 5. 审查："更简单"是合理要求
- 审查结论新增 **`REQUEST_SIMPLIFY`**：正确但比需要的大。Architect 指明要删什么。
- Architect 只有在 Issue 或审查中点名具体风险时，才能要求额外检查、测试或证据。"以防万一"不是风险。
- 审查依据 SHA、测试结果，以及代价低时的独立复算——而不是证据的数量。

## 6. 不变的底线
精确源码 SHA · 如实标注 PASS / FAIL / NOT RUN / BLOCKED · 数值结论使用独立 oracle · 设备结论使用实际观测（而非请求）的设备身份 · 远程会话清理 · 代码和日志中无密钥 · 不伪造结果 · Engineer 不自合并 · 未经用户明确批准不产生新支出。

这些底线**只在此处陈述一次**。其他文档链接到本节，不再重复。
