# 精简证据政策（SAE V3.3）

> [English（正式规范）](../../../governance/LEAN_EVIDENCE_POLICY.md) | **简体中文**

证据的作用，是让独立审查者能够信任结果。所以证据量应当**与风险相称**，并且直接利用 Git 已经提供的保证。出于防御心态额外追加的东西不会增加可信度，反而会消耗 Engineer 的时间和 token、分散审查者的注意力，把真正重要的几条事实淹没掉。例如 2026-10-30，一个只有 25 行的准则函数附带了约 1.7 万行证据。

本政策**减少的是证据数量，不降低证据质量**。§8 列出的底线全部保持不变。

## 1. 完整性由 Git 保证
- 一个确切的提交 SHA 已经唯一确定所有被跟踪文件的每一个字节。
- **不要**为 Git 跟踪的文件另做 SHA-256 清单。
- **不要**另做"tested 与 final 的 blob 一致性"报告。
- 只对 Git 之外的字节计算哈希，并在 handoff 或 summary 里记录它们的 SHA-256 和字节数。这类字节包括：远端下载的产物、构建出的 wheel、外部数据集、提供方返回的输出。

## 2. 只测试最终 HEAD
- 权威验证必须在 PR 最终的源码提交上运行。
- 证据写在 PR 的 **handoff 评论**里；仓库里最多只放 §3 允许的那几个文件。
- 如果之后的提交只改了文档或证据，用一句话说明即可。审查者会用 `git diff --stat <tested>..<head>` 自行核实。

## 3. 按风险等级设定证据上限
| 等级 | 必需内容 | 仓库内证据文件（上限） |
|---|---|---|
| T1 文档 / 配置 | diff，以及能验证这处改动的那一条命令的输出（如果有） | 无 |
| T2 代码 | 测试命令；通过/失败/跳过的数量；一行环境说明；最终 SHA | ≤ 3 个文件，≤ 200 KB（如 `summary.json`、JUnit） |
| 计算 / GPU 实验 | T2 的全部内容，加上实际观测到的设备型号、结论所引用的结果数据、会话清理的读回 | ≤ 10 个文件；原始数据只有在结论引用时才提交 |
| T3 | 由 Architect 在 Issue 中规定并说明理由 | 按规定 |

## 4. 失败记录写成列表，不提交成目录
失败的尝试在 handoff 中按"尝试 — 原因 — 修复"逐条列出。只有当失败本身就是科学结果时，才提交失败日志或目录，例如假设被证伪、可复现的数值崩溃。

## 5. 复用环境检查
- 机器、工具链和固定版本都没变时，不要重复做冷启动或热启动，写一行"环境自 <PR/SHA> 起未变"即可。
- 只重新检查发生了变化的部分；另外，在申请计算资源之前要实时核对账户和会话状态。

## 6. 不做防御性附加工作
额外的探针、快照、备份、dry-run、冒烟测试、基线、夹具或门禁，只在以下两种情况下才加：
- **(a)** Issue 明确要求；
- **(b)** 它直接检验的是这次改动本身引入的风险。

"以防万一"做的工作不算证据。指令有歧义时，选择**较轻的理解**，并用一行字说明你的选择。

## 7. Architect 派工义务
- 每份派工单都要写明简短的**完成标准**和一份**不要求事项**清单。
- Architect 只有在用一句话写明具体风险之后，才可以超出 §3 的上限。
- Architect 审查时依据的是 Git SHA、测试结果和独立复算，而不是清单有多长。

## 8. 不变的底线
- 确切的源码 SHA。
- 如实标注 PASS / FAIL / NOT_RUN / BLOCKED。
- 数值结论要有独立 Oracle。
- 设备相关的结论要有实际观测到的设备型号。
- 远端会话的清理要得到确认。
- 日志中不得出现密钥。
- 不得伪造或改标结果。
- Engineer 不得自行合并。

## 优先级
本政策覆盖项目 Issue、派工单和模板中与之冲突的证据量要求，**除非**该 Issue 已按 §7 明确说明需要额外证据的理由。本政策从不放宽安全、正确性、计费或资源清理方面的要求。
