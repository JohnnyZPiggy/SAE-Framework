# 三文档交接协议：数学、工程、实验

> 语言：[English](../../../workflows/THREE_ARTIFACT_HANDOFF.md) | **简体中文**

## 为什么要建立三类文档？
SAE 通过**三个互相关联的科学研发成果**完成交接，而不依赖聊天窗口记忆或繁琐的日报。这三类文档保存在**每个算法项目自己的 GitHub 仓库**；SAE Framework 母仓库提供的是协议和模板。GitHub Issues/PR 仍负责任务和审查状态。

| 文档及算法项目路径 | 负责人 / 决策权 | 主要回答的问题 | 更新时机 |
| --- | --- | --- | --- |
| **数学研究文档** `docs/research/<algorithm>-tensorization.md` | **GPT 科学导师**与科学家共同研究；**科学家批准** | 原算法有哪些矩阵向量/matrix-free/张量性质？哪些数学等价变换成立？ | 新算法、重要数学改动或新发现 |
| **工程实现文档** `docs/engineering/<algorithm>-engineering.md` | **GPT 总架构师**设定接口和验收；**Codex**记录实现及真实测试；架构师审查 | 代码如何实现？什么被真正测试过？ | 工程设计交接、重要 PR 或版本 |
| **实验验证文档** `reports/gpu/<run-id>/summary.md`，并附结构化结果 | **科学家**实际操作 Colab 并批准发布；GPT 协助实验设计/解释 | 哪个源码 SHA、设备、精度与规模真正完成了验证或加速测试？ | **每次真实实验运行**单独归档 |

## 三段交接契约
- **数学 → 工程：** 数学研究报告由科学家批准 `RESEARCH_READY`（或明确记录有限例外），给出推导、张量形状、参考基线与数值约束；不能未经审核就默认交付性能重构。
- **工程 → 实验：** 工程报告通过实际源码 **commit SHA**、CLI、CPU 正确性证据和架构师的实验矩阵确定下一步 Colab 工作。**CPU 通过不意味着 GPU 通过。**
- **实验 → 数学/工程：** 将精度失败、硬件瓶颈、真实测量反馈给相关 Issue/PR，必要时回到导师研究或 Codex 工程。
- **避免重复：** Issue/PR 管理状态，文档保存数学理由、实现契约与实测证据；性能数字存于实验报告，其他文档通过 SHA/链接引用，不反复复制。
- **学习同步发生：** 导师在这些交接中帮助科学家理解；重要学习成果可记录到对应文档，不强制另写日报。

## 典型迭代
1. GPT 导师推导张量数学结构，形成数学研究报告；科学家审核。
2. GPT 架构师从数学报告定义接口、验收和实验需求，填写工程报告的规格部分或关联 Issue。
3. Codex 实现、真实执行 CPU 测试、更新工程报告并提交 PR；不得自我合并。
4. 科学家在 Colab 针对**指定源码 SHA** 实际运行、核查结果；手动 PR 或已验证 Publisher 将轻量报告上传 GitHub；GPT 辅助解读。
5. 架构师与科学家基于三份文档验收；如果发现新的数学问题可反复回到导师阶段。

## 模板实例化时的链接

将母仓库模板复制为项目正式报告时，必须替换占位符，并**删除或改写模板开头仅在母仓库 `templates/` 位置有效的语言切换链接**，让它指向当前项目固定版本的 `.sae/` 文档。复制到 `docs/research/`、`docs/engineering/` 或 `reports/gpu/` 后，不能假设相对路径还会自动有效。

## 轻量与诚信原则
数学和工程文档是**持续更新的里程碑记录**，无需每次对话复制一份；实验按不同 run-id 分开归档。写清公式、代码、命令、真实结果和链接即可，避免形式主义。

未执行的测试标记 `NOT RUN`；实验报告发布 commit 与**被测试的源码 commit** 必须区分。保留人工授权和可审查 PR，不使用 GitHub Actions，不把 Drive 当同步平台。
